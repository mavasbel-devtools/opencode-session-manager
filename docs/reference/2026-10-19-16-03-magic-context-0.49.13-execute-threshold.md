Evidence for adding Magic Context 0.49.13 to `execute-threshold-min` (`patches/execute-threshold-min.ts`),
read from the published packages on 2026-10-19. Earlier reasoning: from
`2026-10-11-19-37-magic-context-0.47.0-execute-threshold.md` to
`2026-10-18-11-42-magic-context-0.49.12-execute-threshold.md`. This document compares 0.49.13 with
the pristine published 0.49.12 (`npm pack @cortexkit/opencode-magic-context@0.49.12`, integrity
`sha512-y6hmByPA1TJFMx4yfi0amUW/Wh6gjSPax5xKnYHwS0qbsf+MJSEuvUd8lXnDIcVBMbI0dTNu2c31OkhmAKSCEQ==`,

## 2. The schema still rejects values below 20

`package/src/config/` is identical in 0.49.12 and 0.49.13 (`diff -r`, exit 0). The `.d.ts`
declarations under `dist/config/schema/` differ only in the order of the `ask`/`allow` enum members.
Running the 0.49.13 source schema (`MagicContextConfigSchema.safeParse`, zod from the installed
0.49.12 copy) on the live `~/.config/cortexkit/magic-context.jsonc` gives exactly one issue:
`execute_threshold_percentage` "Too small: expected number to be >=20". With that one value set to 20
the configuration is valid.

## 3. The code that uses the threshold is unchanged

Measured with a script over every `.js` file, once in `dist/v2` and once in all of `dist`. Function
texts are brace-matched; whitespace and numeric identifier suffixes are normalised.

- Identical function texts in both versions: `resolveExecuteThresholdDetail`, `modelKeyLookupOrder`,
  `resolveTokensMatchWithKey`, `resolveModelKey`, `resolveContextLimit`, `isFinitePositive`,
  `normalizeTrustedPercentageThresholds`, `makeProjectThresholdWarning`, `resolveHistoryBudgetTokens`.
- All call sites of `resolveExecuteThresholdDetail(` (7 in `dist/v2`, 16 in `dist`) are identical
  with 300 characters of context on each side.
- Every `executeThresholdPercentage: …` assignment (8 in `dist/v2`, 12 in `dist`) is the same.
- Every expression mentioning `executeThresholdPercentage`, `execute_threshold_percentage` or
  `ExecuteThreshold`, with 60 characters on each side and digits removed: 90 in `dist/v2` and 198 in
  `dist` in both versions, none different.
- `MAX_EXECUTE_THRESHOLD = 90` and `PROACTIVE_TRIGGER_OFFSET_PERCENTAGE = 2` are unchanged, so 13
  still gives 11. `EXECUTE_THRESHOLD_CAP_MESSAGE` appears 4 times per build, as before.
- The log lines `effect` reads are present as in 0.49.12 (per build): "transform threshold: model="
  (1), "proactiveFloor=" (1), "below proactive floor" (2), "config reload failed" (1).
- Functions other tools rely on are unchanged: `seedV2ForkFromParent`, `openDatabaseAsync`.

## 4. Storage and release notes

`LATEST_SUPPORTED_VERSION = 95`, highest migration `version: 95`, in both builds. The release notes of
v0.49.13 state "No migration. `context.db` stays at schema 95 and `store.db` at schema 63". The
behaviour changes they list are relevant to the threshold only by absence: memory verification works
in batches of five with a four-minute deadline, the retrospective runs less often, queued removals
survive a failed turn, the final answer after tool use is kept in memory mapping, and OpenCode 2
verification gains code-navigation tools.

So the same three replacements make a configured 13 work as 13 on 0.49.13. The e2e test
`tests/e2e/lifecycle.test.ts` applies and undoes the patch on the fixture files and checks both
checksums. After updating to 0.49.13: `opencode-magic-context-patches apply`, restart OpenCode, then
`opencode-magic-context-patches effect` (expects `respected`).
